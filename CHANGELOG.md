# Changelog

All notable changes to this project are documented in this file.

The format is based on [Keep a Changelog](https://keepachangelog.com/en/1.1.0/).

## [Unreleased]

### Added

- **Per-book Edge TTS voice selection (the Generar Audiolibro picker now drives real voices)**: the "Voz TTS" picker — which until now offered macOS `say` voices (Paulina, Samantha…) that the Edge-TTS backend never used — is now a list of REAL Edge TTS short voices (es-MX Dalia/Jorge/Beatriz/Catalina/Emilio, es-ES Elvira/Álvaro/Laia/Pablo/Abrela, en-US Emma multilingual/Aria/Guy, default = `es-MX-DaliaNeural`). `PUT /api/files/{bookId}/tts-voice` persists the choice on the Book (bulk update — the `full_text` CLOB is never loaded; `null` clears back to the default), validating the short-name format (`es-MX-JorgeNeural`) BEFORE touching the DB — a macOS voice name like "Paulina" gets a 400. The audio step reads the voice from the SAME light `BookAudioView` projection and threads it down to the synthesis: `EdgeTtsClient.synthesizeToFile(text, path, voiceOverride)` resolves the override per call (the client is a shared singleton and several audiobooks synthesize in parallel — the voice NEVER lives in a mutable field). Once set, the voice applies to EVERY future audio run of the book, including the novels manager's "Crear Audio" (a manager volume and its Book are 1:1). The page's generate flow saves the voice first and then triggers the AUDIO stage; the confirmation toast names the chosen voice.
- **Audiobook download in the novels manager**: volumes with generated audio get a "Descargar Audio" button (enabled by the existing `audioCreated` flag). `GET /api/novels-manager/volumes/{id}/audio/download` resolves the volume → linked Book → the DB's audio pointer (light `BookAudioView` projection — the `full_text` CLOB is never touched; the path NEVER comes from the request) and streams the result without ever materializing it in memory: a block-based audiobook directory is zipped ON THE FLY (only regular `*.mp3` files, reading order preserved by the 01/02 name prefixes; a full volume can be hundreds of MB), and the legacy single-file audio streams as `audio/mpeg`. `Content-Disposition` carries a UTF-8 `filename*` (book names have spaces and brackets). Distinguishable errors: 404 for unknown volume/Book/no audio, 409 when the DB points at files that vanished from disk (the flag only reflects the DB pointer — deletions happen). The button uses a `_blank` anchor: an attachment download never leaves the page, and errors open visibly in a new tab instead of breaking the table.
- **Manual audiobook generation with a translated-book picker (translation no longer chains into audio)**: the "Generar Audiolibro" page gains a combo box listing ONLY fully-translated books (`totalChunks > 0 && completedChunks === totalChunks`, from the new chunk-progress fields of `GET /api/files/list` — one grouped `countByBookIds` query for the whole list, zero N+1), sorted with the audio-less books first and a "✔ audiolibro" marker for those already generated; the "Generar Audiolibro" button runs the AUDIO stage only (`POST /files/{id}/process?to=AUDIO` — the same independent-stage contract the novels manager uses: resumable, blocks with files on disk are skipped). The automatic Translation→Audio workflow is gone from the UI: the Historial "Iniciar/Reanudar" button now resumes TRANSLATION ONLY (`to=TRANSLATE`, labels "Traducir"/"Reanudar traducción") and the service method that chained the full pipeline was removed. Deliberately unchanged: the dashboard's Arrancar (operator full-resume — it's what recovers a book from any checkpoint) and the startup crash-recovery (resuming interrupted work, not a new-work workflow).
- **Video Stories wizard**: end-to-end multi-step assistant (`VideoStoryWizardController`) that turns a premise into a video-story project — design → scenes → assets → video steps (`Wizard*StepRequest` DTOs), a dedicated prompt factory (`VideoStoryPromptFactory`), projects persisted through `VideoStoryProject`/`VideoStoryProjectRepository`, and its own Angular section (`/video-stories`) wired into the routes and the app menu.
- **Per-use-case AI provider selection (nvidia | ollama), hot-swappable and persistent**: `AiProviderSettingsService` + `AiProviderConfig` persist the provider chosen for translation and for stories (surviving restarts); `NvidiaAiService` reads the selection live and routes each call to the NVIDIA pool or the 100% local Ollama pool. `AiProviderController` exposes the selection and the Settings page (`settings.ts` + `ai-provider.service.ts`) switches providers without a restart.
- **Per-chunk failure cause, surfaced live**: `Chunks.errorMessage` (VARCHAR 4000) persists the concise cause chain of every failed translation (cleared on retry) and reaches the FE through the extended `ChunkDto`; the Traducir Libro page raises a sticky popup for every chunk that turns FAILED in vivo (only the new ones — a baseline is kept) with the exact cause. Error toasts across the app (glossary, novels manager, regex patterns, upload steps, uikit) became sticky with a 12 s default life.
- **Elsione discovery chart in the status panel**: a 14-day gap-filled series of novels/volumes discovered per day (`CatalogActivityPointDto`), computed with two native H2 GROUP BYs over `created_at` INSIDE the already-cached `CatalogStatsService.catalogStats()` (two no-arg `@Cacheable` methods in the same cache would collide on `SimpleKey.EMPTY` — the series shares the `catalogCounts` cache and its sync eviction by design), rendered by a full-width dashboard widget with grouped bars (novels vs volumes) and the catalog totals in the header.
- **Operable process panel (states + pause/stop/start)**: the dashboard Processes widget lists every non-COMPLETED book with its state (Running / En espera / Detenido / Fallido) and a `running` flag that separates real in-memory runs from stale statuses (crash leftovers), plus manual actions: **Pausar** (cooperative — the step in flight finishes completely and the run stops at the next checkpoint leaving the book AWAITING, consuming zero retry budget), **Detener** (immediate — in-flight chunk translations are cancelled via `cancelActiveTasks`, the book is marked STOPPED with a guarded bulk update for instant UI feedback, and the step closes as CANCELLED in the trace), and **Arrancar/Reanudar** (resumes from the last checkpoint and wakes STOPPED books — the startup auto-resume keeps ignoring them by design; STOPPED was previously a dead status nobody ever set). New endpoints `POST /api/files/{bookId}/pause` and `POST /api/files/{bookId}/stop`; the elscione sync row gains Arrancar/Cancelar. New `TraceEventStatus.CANCELLED` + `ProcessingTraceService.cancelStep` close interrupted steps without counting toward the genuine-failure budget (a user stop is never a model failure), rendered in the trace timeline as "Cancelado".
- **Per-process deep-link into the live log viewer**: every process row (and the sync row) has a "Ver logs" button that lands on `/logs` with the filter preset — `?book=` presets the MDC trace filter (catches the book's runs AND its per-chunk translations, whose `traceId` is the chunk but whose `bookId` always travels), `?text=` + `?clearExclude=1` expose the sync events (they carry no MDC bookId and are hidden by the viewer's default exclusion), and `?name=` feeds a dismissible header chip that restores the defaults and strips the query params on click.
- **Model investigation (specs + online pre-flight)**: the app now investigates a model BEFORE using it — real specifications and availability. For local Ollama models: `POST /api/show` gives the full specs (context length extracted by the `.context_length` SUFFIX because the key is architecture-dependent: `gpt-oss.context_length`, `llama.context_length`, ...; also parameter count, quantization, family, capabilities — a `thinking` capability confirms the model reasons and consumes part of its output budget, validating the reasoning-reserve design). For NVIDIA: `GET /models` with the API key — a cheap online probe (provider reachable? key valid?) and the published catalog of model ids, verified against the rotation pool (catches EOL'd or misspelled models before the first call). `GET /api/models` surfaces the whole investigated catalog. Probes have short connect timeouts (3 s) and a TTL cache (60 s).
- **6-model NVIDIA rotation pool with GLM-5.3 as primary, local Ollama gpt-oss:20b as ultimate fallback**: `z-ai/glm-5.3` (primary) → `openai/gpt-oss-20b` → `nvidia/nemotron-3-super-120b-a12b` → `z-ai/glm-5.3-flash` → `deepseek-ai/deepseek-v4.1-flash` → `moonshotai/kimi-k3` → `ollama:gpt-oss:20b` (last resort). Provider-aware pre-flight: NVIDIA models probe `isNvidiaOnline()`, Ollama models probe `isOllamaOnline()` (localhost, no DNS dependency). With NVIDIA online, the rotation resets its skip counter and the local model is never reached; with NVIDIA offline, 6 WARN-skips (zero quota) fall through to the local model via direct HTTP to `POST /api/chat` on localhost:11434 (bypassing both the network and the NVIDIA API); both offline → fast-fail. Ollama's `done_reason="length"` is translated to the same `TranslationTruncatedException` so the piece self-healing works identically for both providers.
- **Multi-step literary translation prompt protocol**: a 4-step protocol (analyze → clean → translate → refine) replaces the single-paragraph prompt — persona (world-class translator + literary editor), pre-correction of extraction artifacts with a never-invent constraint and a bracketed corruption marker, aggressive pruning of non-narrative debris (page numbers, ISBNs, credits) while preserving chapter headings, honorifics guidance for J/C/K novels, tag integrity, strict output discipline, and paragraph preservation (the parallel viewer, per-block TTS and the manuscript depend on `\n\n`). Language-parameterized (fixes the old prompt's hardcoded "idiomatic Spanish"). The series glossary block is injected into Step 3 as established terms that must not be re-translated.
- **Output-token budget strategy with paragraph-aware piece splitting and truncation self-healing**: the constraint that corrupts a translation is the model's OUTPUT token cap (the visible translation and internal reasoning tokens share the same response budget), not the input (131 K context). Every request now sends `.maxTokens(8192)` explicitly; oversized texts split into pieces at paragraph boundaries (a degenerate giant paragraph cuts at sentence boundaries and rejoins with " " so no fake breaks are invented); if the model still truncates (`finish_reason=length`), the piece re-divides at half its size and retries recursively (1000-char floor → visible FAIL). Config: `app.nvidia.{max-output-tokens, reasoning-reserve-tokens, chars-per-token, translation-expansion-factor}`.
- **Real-time translation progress bar**: the Traducir Libro page shows a progress bar card during an active run — completed/total chunks, percentage, chunks currently PROCESSING, and a last-updated timestamp — auto-refreshed every 3 seconds. Starts when the user launches "Iniciar Traducción", resumes for already-PROCESSING documents, stops with a final toast. The per-chunk "Traducir chunk" button keeps its own individual spinner.
- **Observable model-call lifecycle in NvidiaAiService**: `[llm] Llamando al modelo X (prompt de Y caracteres, intento Z/W)` at INFO before each attempt, `Respuesta de X: N caracteres en D ms` at INFO on success, WARN on every retryable rotation, `[traducción]` prefix on budget/split events — all inside the chunk worker's MDC so the live viewer and the BD history can follow every call.
- **Elsione per-folder completion flags with resumable sync passes**: every novel folder listed completely in a pass is flagged (`Novel.listingComplete` + `lastListedAt`); the next runs SKIP those folders (one preload query per run, O(1) lookups in the walk — a saved HTTP listing + anti-ban pause per folder) and only list the pending ones, the always-cheap category folders and the root. A cancelled run resumes exactly where it stopped, and skipped folders still count as visited so their volumes are not marked removed. When 100% of the folders are flagged (local catalog mirrors the server), the next run resets every flag with one bulk update and starts a full cycle again. The sync status exposes the cycle (`fullCycle`, `foldersComplete`, `foldersPending`, `skippedFolders`) and every milestone is logged ("Pasada incremental: 79/1343 carpetas completas…", per-folder skips, per-novel upsert detail).
- **Multi-class log filtering**: the live viewer's class filter became a multi-select (several classes at once, with counts), and `GET /api/logs/search` accepts a comma-separated `loggers` parameter (typed IN predicate — an untyped `root.get(...)` silently matches nothing in Hibernate 6).
- **Exhaustive backend logging, fully javadoc'd**: milestone INFO logs for `saveBlocks` (blocks + rebuilt clean-text size), both split variants (chunks per block / whole text), `deleteBook` (rows removed per table), the translation dispatch (pending chunks) and the audio synthesis (chars, fragments, target) — completing the pipeline coverage (step transitions, per-chunk translations, catalog sync) so every operational flow is now traceable in the live viewer and the persisted history.
- **Glossary extraction now routes through the model rotation** (`callModelWithRotation`): it inherits the full model pool, the explicit output cap, the truncation self-healing, the shared 30 RPM quota and the `[llm]` log lines. Spring AI's `.entity()` replaced by a robust Jackson parser that extracts the JSON from code fences.

### Fixed

- **Re-saving the semantic block division no longer blows up with FK 23503**: `saveBlocks` (the Dividir Texto page) bulk-deleted the book's blocks WITHOUT clearing the block-bound chunks first — re-editing the division of a book that already had chunks from a previous split left orphan chunks pointing at the doomed blocks and the FK `chunks.block_id` killed the whole save ("Referential integrity constraint violation … delete from blocks where book_id=?"). The bound chunks are now bulk-deleted BEFORE the blocks (`deleteBoundByBookIdInBulk`: only `block is not null` — the legacy unbound whole-text chunks are untouched), matching `deleteBook`'s order (which already did chunks → blocks). The stale chunks of a dying division are obsolete by definition: the split regenerates them from the new blocks.
- **The log-persistence flush loop is de-poisoned and LOG_EVENT's legacy columns are widened**: a legitimate 470-char log message (Spring's "Serializing PageImpl instances as-is is not supported…") blew the INSERT because the table's MESSAGE column was VARCHAR(255) — the LogEvent entity declared NO column lengths, so hbm2ddl created every string at 255 and never widened it (the javadoc's "VARCHAR(8192)" was never real). The failed transaction had ALREADY assigned the UUIDs (Hibernate generates them pre-commit), so the re-enqueued batch carried ids of rows that never existed: every retry became an UPDATE of a nonexistent row — "Row was already updated or deleted by another transaction" — bouncing the same batch forever (403 warnings over 2 hours in production, the loop still alive when fixed). Two-part fix: the retry now CLEARS the id of every re-enqueued event (the next saveAll is a clean INSERT with a fresh UUID), and the DatabaseIndexInitializer widens LOG_EVENT's columns to the entity's declared lengths at startup (MESSAGE 8000, LOGGER 256, THREAD 128, BOOK_ID/TRACE_ID 64, STEP 32 — rows preserved, idempotent). The entity now declares @Column(length) explicitly, aligned with capture()'s truncates (LOGGER's 256 was also over the legacy 255). Live-verified: one final poisoned warning after the fix deployed, then silence — the queue drained with clean inserts.
- **The audiobook-generation task now shows in the Processes panel, with pause/stop that take effect between blocks**: two bugs hid it. (1) The orchestrator's entry guard silently swallowed manual AUDIO-stage runs on COMPLETED books ("is already completed; nothing to do") — the Generar Audiolibro button responded 202 "started" and nothing ever ran, so nothing appeared in the panel; a manual `to=AUDIO` run is now the ONLY exception that passes the guard (the audio regeneration is legitimate: new voice, deleted mp3s) and the book is restored to COMPLETED afterwards (or left AWAITING if the user paused mid-generation). (2) Pause/stop during the audio step only took effect after the WHOLE step (an entire audiobook); they now take effect at the NEXT BLOCK boundary, the step closes as CANCELLED in the trace with the kept-mp3s count (no retry budget consumed), and reanudar skips the blocks that already have their mp3. A missing pause checkpoint between the AUDIO and FINALIZE steps let a paused full run slip through to FINALIZE — fixed and locked by a regression test.
- **cancelStep exploded at persist time on the long-lived H2 file — the trace STATUS column is a NATIVE H2 ENUM carrying the 4 values TraceEventStatus had at table birth**: adding CANCELLED to the Java enum never updated it, so every pause/stop degraded into a FAILED run ("Valor no permitido para la columna … 'CANCELLED'"). The DatabaseIndexInitializer now migrates the column at startup (re-declares the ENUM with the full 5-value list; multi-connection verified, rows preserved) and also removes stale CHECK-constraint vintages — dropped, NOT replaced: H2 2.4.240 (the runtime version) has a multi-session regression where a CHECK re-created after a drop is enforced with the STALE expression on other connections (works on 2.3.232 and in single sessions; verified with a standalone probe).
- **Edge TTS Sec-MS-GEC v2 DRM (Microsoft's October 2026 rollout)**: Microsoft deployed a v2 of the Edge Read Aloud DRM token and the legacy v1 token gets HTTP 403 on every WebSocket handshake in the regions where the staged rollout is already active (upstream edge-tts issue #490, opened 2026-10-10; the 2026-10-17 Vol. 19 audio pass died on it after the TRANSLATE step had completed all 44 chunks). The Java port now generates the v2 token format `<16 hex CS64>-<64 hex modified SHA-256>` — `EdgeTtsDrm` is a line-by-line port of edge-tts 7.3.1's drm.py (custom mid-stream SHA-256 state, schedule constants with sigma adjustments, adjusted round constants, CS64 keyed checksum) with every 32-bit value kept as a masked long so each masking point reproduces the Python reference bit-for-bit; the ticks keep the exact float path (recomputing them with integer arithmetic changes the string for some timestamps and breaks the CS64 half). `SEC_MS_GEC_VERSION` declares `2-143.0.3650.75`; the host, UA and every other protocol constant stay unchanged — the token is the fix, not the endpoint. Validated two ways: byte-for-byte against the upstream Python reference on fixed timestamps (JUnit reference vectors), and live — a real synthesis against Microsoft's service completed in 1.9 s, and the interrupted Vol. 19 audiobook resumed straight from its AUDIO checkpoint.
- **410 Gone model EOL no longer kills pieces nor cascades (kimi-k3 incident)**: `moonshotai/kimi-k3` reached NVIDIA end-of-life and every call died with `410 Gone`; the old classification treated it as non-retryable — killing the chunk — AND left the rotation index stuck on the dead model, so every subsequent chunk landed on it too (10 dead chunks in one pass). New `isModelGone` category (SDK-typed `OpenAIServiceException.statusCode()` 410/404 walked through the cause chain, plus message fallbacks including the local "Ollama HTTP 404") is checked FIRST in the rotation catch: a dead model rotates to the next one and advances the index, consuming an attempt so a pool full of dead models still terminates. kimi-k3 left the pool (replaced by `meta/llama-3.2-90b-vision-instruct`).
- **Pieces that don't fit the server's time ceiling now re-divide themselves**: generations exceeding NVIDIA's ~240 s server limit fail as "Request failed" at ~243 s, and the old behavior rotated through the whole pool burning ~4 minutes and one RPM unit per model (sometimes exhausting all 21 attempts). The rotation now counts slow timeouts (`countsAsSlowFailure`: retryable failure + duration ≥ `app.nvidia.slow-piece-threshold-seconds`, default 240 — network blips fail in seconds and never qualify) and after `app.nvidia.slow-piece-max-failures` (default 2) throws `PieceGenerationTooSlowException`, which funnels the piece into the SAME self-healing as the truncated case: halve at paragraph boundaries (`translateHalves`, now shared by both paths), each half opens a fresh rotation with its own retry budget, converging under the ceiling (21.8 K → 10.9 K → 5.5 K chars; the 1000-char floor propagates visibly instead of halving forever).
- **Explicit 5-minute model-call timeout pinned** (`spring.ai.openai.chat.options.timeout: 5m`): Spring AI 2.0.1 ships an implicit 60 s default that is NOT applied to chat calls (proven empirically by successful 102-133 s calls in production; bytecode inspection of `OpenAiChatModel`/`SpringAiOpenAiHttpClient` confirms it builds no `RequestOptions` with it), but a future version could start honoring it and instantly kill every long-but-legitimate call. 5 min sits above the observed ~240 s server ceiling, so it can never become the binding constraint.
- **ffmpeg merge deadlock + fixed 10-minute TTS cap in the audio path**: the ffmpeg concat of a full audiobook could fill the ~64 KB subprocess pipe (banner + progress stats go to stderr with the default ProcessBuilder pipes), blocking ffmpeg forever and hanging the AUDIO step with the book stuck in PROCESSING and the re-entrancy guard held. Output is now discarded (`redirectErrorStream` + `Redirect.DISCARD`) and the merge is bounded by `app.audio.merge-timeout-minutes` (default 15) with `destroyForcibly()` on expiry. The fixed `allOf(...).get(10, MINUTES)` TTS cap — which systematically failed legitimate whole-book runs (500+ fragments at 3-way concurrency) — now scales with the fragment count (waves × connect+receive ceiling per fragment, floor `app.audio.tts-min-total-timeout-seconds`).
- **CLOB-free AUDIO step**: the audio step materialized the book's multi-megabyte `full_text`, every block's chapter-length `content` and BOTH text columns of every chunk — then rewrote the CLOBs through the dirty-check flush of `save()`. It now runs entirely on light projections (`BookAudioView`, `BlockAudioView`, `BlockChunkAudioView`, and the scalar `findTranslatedTextByBookId` ordered by position) and persists audio paths with bulk updates (`updateAudioPathInBulk`) — the same design the TRANSLATE step already used for dispatch.
- **Orphan PROCESSING chunks are cured on startup**: when translation threads die with the instance (crash, devtools restart, shutdown mid-call), the PROCESSING rows stayed frozen — a lying "Traduciendo" badge, a permanently disabled per-chunk button, and no log activity. `ProcessingStartupRecovery` now requeues every orphan PROCESSING chunk to AWAITING with a global bulk update at startup (before resuming books), logging the healed count. The `@PreDestroy` flush of the log persistence was also validated in production (5 events persisted during a real shutdown).
- **`ddl-auto: update` could not add the flags columns to the existing `novel` table** (NOT NULL on 1,347 populated rows without a DEFAULT is silently skipped by hbm2ddl): the idempotent `DatabaseIndexInitializer` now also guarantees column additions (`ALTER TABLE ... ADD COLUMN IF NOT EXISTS ... DEFAULT FALSE NOT NULL`), backfilling existing rows at startup.
- **Scope-reactive Traducir Libro page with per-chunk translation**:
  - The parallel original/translation view is now scope-aware: "Libro completo" shows every chunk in deterministic reading order (block position, then chunk position within it) instead of the previous unsorted page, and each chunk is badged with its owning Prólogo/Capítulo/Epílogo block (the long-pending block badge of the block-scoped design); "Bloques específicos" lists the marked blocks progressively (chips panel) and filters the chunk view live to the marked blocks as they are checked.
  - New per-chunk "Traducir chunk" action: `POST /api/files/{bookId}/chunks/{chunkId}/translate` validates book, chunk ownership and text, reuses the book glossary and dispatches through `ChunkTranslationService` (own virtual thread, shared 30 RPM quota, short transactions — the pipeline's exact dispatch path). A COMPLETED chunk can be re-translated and nothing else is touched; 409 while a pipeline pass runs. The UI polls per chunk (2.5 s up to 60 s) with a per-chunk spinner.
  - `GET /api/files/{bookId}/chunks` accepts an optional comma-separated `blocks` parameter (scope-filtered view) and returns block metadata per chunk through the new LOB-free `ChunksRepository.ChunkView` projection (LEFT JOIN — block id/type/number reach the UI without loading the block content CLOB).
- **Traceable chunk translations and a noise filter in the live log viewer**: `ChunkTranslationService` now logs the full per-chunk lifecycle ("Traduciendo chunk X (N caracteres)" / "Chunk X traducido (A → B caracteres, D ms)") with the pipeline MDC keys (bookId / traceId=chunkId / step=TRANSLATE) filled inside the async worker — manual single-chunk requests and every chunk of a full run are now visible and filterable in the live viewer (previously nothing but errors appeared). The request itself is audited ("Traducción individual solicitada: chunk X del libro Y (N caracteres, estado previo: S)"). The viewer gains an "Excluir (clase o texto)" filter, defaulted to `NovelsCatalogSync`, so the elscione batch lines stop burying the pipeline events. Manual single-chunk translations deliberately do NOT write `ProcessTraceEvent` rows (they would consume the TRANSLATE retry budget).
- **Database log history with 7-day retention**: Logback events (from `app.log-persistence.min-level`, default INFO — DEBUG stays live-only) persist to the new `log_event` table for post-mortem analysis. A second root-logger appender (`LogEventDbAppender`, attached at `ApplicationReady` like the stream one) feeds a bounded in-memory queue (20k, drop-on-overflow with a rate-limited warn — logging never blocks); a self-managed virtual-thread scheduler flushes batches of up to 1000 rows every 5 s with a single `saveAll` (a DB failure re-enqueues the transactional batch and retries — no losses, no duplicates; a final flush runs on shutdown), and a purge at startup plus daily bulk-deletes everything older than `app.log-persistence.retention-days` (default 7). The pipeline MDC is stored as first-class columns (`book_id`, `trace_id`, `step`) with `(logged_at)`, `(book_id, logged_at)` and `(level, logged_at)` indexes; messages are truncated to 8000 chars in a searchable VARCHAR. Analysis endpoint: `GET /api/logs/search?from=&to=&level=&bookId=&q=&page=&size=` (JPA Specification filters, newest first) returns the viewer's `LogEventDto` shape.

- **Database optimization pass (queries, indexes, caches)**:
  - **Query-driven composite indexes**, declared on the entities and guaranteed on the long-lived H2 file by the new `DatabaseIndexInitializer` (idempotent `CREATE INDEX IF NOT EXISTS` + `ANALYZE` on startup): `novel(title)`, `blocks(book_id, position)`, `chunks(book_id, status)`, `chunks(block_id, position)` and `process_trace_event(book_id, step, started_at)` — each annotated with the query pattern it serves.
  - **Caffeine cache layer** (`CacheConfig` + `spring.cache`): `regexPatterns` (cleaning patterns read on every text extraction, evicted by the pattern CRUD) and `catalogCounts` (dashboard novel/volume COUNTs, evicted whenever a catalog sync run finishes), replacing the hand-rolled racy 60-second TTL pattern cache in `TextExtractorService`.
  - **`OptimizedQueriesTest`**: a `@DataJpaTest` integration suite (11 tests) that exercises every new projection, bulk update and bulk delete against real H2 and asserts the composite indexes exist in the schema.
- **Shared NVIDIA rate limiter** (`NvidiaRateLimiter`, `app.nvidia.rate-limit-rpm: 30`): token bucket with full initial capacity and one permit every `60/rpm` seconds; `acquire()` blocks (virtual threads park) until quota is free. Applied at both API chokepoints — every model attempt in `NvidiaAiService.callModelWithRotation` (including retries and key rotation) and glossary extraction in `GlossaryService` — so translation, retries and extraction share one orchestrated budget across the whole pipeline. `rpm <= 0` disables the limiter.
- **Configurable parallel TTS** (`app.audio.tts-concurrency: 3`): `AudioGeneratorService` synthesizes a block's internal ~1000-char TTS fragments concurrently toward the Edge TTS endpoint and merges them in order afterwards.
- **`ChunkTranslationService`**: dedicated bean for per-chunk translation, invoked through the Spring async proxy.

### Changed

- **Virtual-thread executor**: `bookProcessingExecutor` switches from a 4–8 platform-thread `ThreadPoolTaskExecutor` to `SimpleAsyncTaskExecutor` with `setVirtualThreads(true)` (Java 21). Pipeline tasks — orchestrator runs, chunk translations, audio — park for free during NVIDIA/Edge-TTS/LLM waits instead of pinning platform threads. The `MdcTaskDecorator` is preserved, so every log line still carries `bookId`/`traceId`/`step` for the Visor de Logs.
- **Truly parallel chunk translation**: every pending chunk translates on its own virtual thread with the glossary injected, paced by the shared limiter.
- **LOB-free pipeline reads**: `Book.fullText` (up to ~578 KB per book) used to ride along with every `findById` — orchestrator entry/steps, `startStep`/`skipStep` checkpoints, the `/list` and `/{id}/status` endpoints, startup recovery and the glossary FK link. All of those now read light projections (`findStatusViews`, `findBookListViews`, `hasExtractedText` via `LENGTH(TRIM(full_text))` in SQL) or move state with bulk updates (`updateCheckpoint`, `updateStatusWhen`, `updateStatusAndTrace`, per-block `updateAudioFilePath`); trace attempt counting is a single `COUNT` instead of loading every event, and the glossary links its Book FK via `getReferenceById`.
- **TRANSLATE step on light projections**: pending-chunk evaluation reads only (id, status, attempts); stale requeue, legacy attempt healing and post-failure accounting are single bulk UPDATEs; the dispatch list is an id-only query. Chunk texts are loaded solely by the translating virtual thread, and the per-block audio step loads all blocks' chunks in ONE query.
- **No DB transaction around LLM calls**: `translateChunk` and `processBookChunksAsync` no longer declare `@Transactional`, so no Hikari connection stays pinned during the NVIDIA API call (seconds to minutes at 30 RPM); each persistence step runs in its own short transaction. This removes the connection-pool saturation risk of the parallel chunk translation.
- **N+1 elimination in the novels manager**: one grouped volume-count query per catalog page (was one COUNT per novel), one grouped total/completed chunk-count query per page (was two COUNTs per volume), one `findByVolumeIdIn` for all files (was one query per volume) and batched book status views — no per-volume lazy `Book` load of the `full_text` CLOB anymore.
- **Batched catalog sync**: volumes and files accumulate and flush in one `saveAllAndFlush` per kind instead of one `saveAndFlush` round-trip per row; novels that disappear from the source are marked with a single bulk UPDATE instead of paging every novel and saving each volume.
- **JDBC batching + dirty-write hygiene**: `hibernate.jdbc.batch_size=25` with `order_inserts`/`order_updates`, `@DynamicUpdate` on hot entities, and `saveAll` for chunks/blocks/glossary terms (was one `save` per row). Derived `deleteAllBy*` became bulk `deleteBy*InBulk` JPQL deletes (no entity loading before delete), all `@Modifying` operations use `flushAutomatically`/`clearAutomatically` so the persistence context never serves stale rows.
- **Database/runtime tuning**: `spring.jpa.show-sql: false`, `spring.jpa.open-in-view: false`, and the H2 URL gains `CACHE_SIZE=65536` (64 MB page cache for the ~24 MB database, default was 16 MB).

### Fixed

- **The Dividir Texto editor could silently destroy a document**: `saveBlocks` rebuilds `full_text` solely from the marked blocks, so saving with zero, one or a few blocks marked discarded every unmarked paragraph forever — the balance validation only guaranteed matched tags. This is exactly how Volume 19 lost its 25 translated chunks. The editor now measures the text that would be discarded (mirroring the exact parse regex) and blocks the first Guardar with a warning that includes the character count; a second explicit click proceeds, so intentionally dropping short junk remains possible.
- **Two latent persistence bugs caught by the new log-history tests before shipping**: a pre-assigned `@GeneratedValue` id made `saveAll` treat new rows as detached entities and issue an UPDATE of a missing row (`ObjectOptimisticLockingFailure`), and Hibernate 6 silently ignores predicates added via `cb.conjunction().getExpressions().add(...)` (the generated SQL kept `where 1=1`, which would have disabled every `/api/logs/search` filter) — ids are generated on persist and specifications now combine filters with `cb.and(...)`.
- **Deep links and reloads on client routes returned a JSON 500**: `/pipeline/translate-book` (and `/logs`) are Angular client-side routes, but the SPA fallback in `WebConfig` only covered a hardcoded prefix list — a reload or bookmark on any pipeline route fell through to the static-resource handler and surfaced `NoResourceFoundException` as `{message: "An unexpected error occurred.", details: "No static resource pipeline/translate-book ..."}`. `GlobalExceptionHandler` now handles `NoResourceFoundException` explicitly: every non-API, non-asset path (no `/api`, `/api-docs`, `/swagger-ui`, `/h2-console`, `/error` prefix, no file extension) forwards to `index.html` so the Angular router boots into the right page; genuine misses (unknown API endpoints, broken asset links) get a proper 404 JSON instead of the generic 500. Verified live: `/pipeline/translate-book` and `/logs` serve the app shell (200), `/api/unknown` returns 404 JSON, and the catalog API keeps working.
- **Re-sync could drop volume metadata**: the batched upsert only persisted brand-new volumes, so the refresh of `label`, `translatorGroup` and the `removedFromSource` reset of existing rows relied on dirty checking and could be silently lost; every touched row is now persisted and flushed explicitly.
- **Sequential self-invocation defect**: `processBookChunksAsync` called `translateChunkAsync` via `this.`, bypassing the `@Async` proxy — so chunks translated sequentially despite the async annotations. Chunk translation now goes through the `ChunkTranslationService` proxy.

Measured on a two-chunk book: ~44s total with two interleaved virtual threads vs ~88s sequential. 78/78 tests green, including the new `NvidiaRateLimiter` and `ChunkTranslationService` suites. Database pass verified with 334/334 tests green (11 of them the new H2 integration suite); the SPA deep-link fix brings the suite to 340/340.
